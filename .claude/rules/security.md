# Security rules

All durations, limits and keys below are properties under `libryx.security.*` and
`libryx.rate-limit.*` (catalog in `docs/configuration.md`). Never hardcode them.

## Access model

- **Stateless** API: no HTTP session, CSRF disabled.
- **Everything requires a valid access token**, including the catalog. The only public endpoints are:
  `POST /api/auth/register`, `/api/auth/verify-email`, `/api/auth/verify-email/resend`,
  `/api/auth/login`, `/api/auth/refresh`, `/api/auth/password-reset`,
  `/api/auth/password-reset/confirm`, plus `/actuator/health` and `/actuator/info`. Swagger UI is
  public only in the `local` profile.
- Authorization with `@PreAuthorize` on each operation; do not rely on URL rules alone.
- CORS limited to the frontend origin (`http://localhost:4200` locally), set by property, with
  credentials allowed so the refresh cookie can travel.

| Role | Can |
|---|---|
| `ADMIN` | Everything a librarian can, plus users, roles, personal data and RAG management |
| `LIBRARIAN` | Catalog, requests, loans and sanctions. **No access to personal data** |
| `USER` | Browse the catalog; request, cancel and renew **their own** loans |

- A `USER` reaches only their own resources: check ownership against the authenticated user, never
  against a `memberId` from the request. Someone else's resource answers 404, not 403.
- **Personal data** (`user_profiles`: document id, phone, address, birth date, admin notes) is exposed
  only by `/api/admin/users` with `hasRole('ADMIN')`. Never in other modules' DTOs, logs or the assistant.

## Registration and email verification

- **Self-registration** is public and always creates a `USER`. The role is never read from the request.
- Registration creates `users` (`email_verified = false`) and `user_profiles` together. The member
  number (`LBX-000123`) is generated by the server from the user id, never supplied by the client.
- Staff accounts (`LIBRARIAN`, `ADMIN`) are created only by an `ADMIN` through `/api/admin/users`.
  How a staff member sets their first password is **not defined yet: ask before implementing it**.
- **Email verification is mandatory to sign in.** Registration sends a random 6-digit code, valid for
  15 minutes and single-use. Only its hash is stored (`email_verification_codes.code_hash`), with an
  attempt counter: 5 failed attempts invalidate the code.
- Signing in with correct credentials but an unverified email answers 403 `EMAIL_NOT_VERIFIED`. Check
  the password first, so the response never reveals whether an account exists.
- Resending a code follows the same limits as password recovery.

## Passwords and sign-in

- Password policy, enforced at registration, reset and change: 8 to 64 characters with at least one
  upper-case letter, one lower-case letter and one digit.
- Hash with the configured `PasswordEncoder`. Never store, log or return a password.
- Wrong email and wrong password give the same 401 `INVALID_CREDENTIALS`.
- Account lockout: 5 consecutive failures lock the account for 15 minutes (`failed_login_attempts`,
  `locked_until`). Only `ACTIVE` accounts can sign in (`ACTIVE`, `INACTIVE`, `BLOCKED`).

## Tokens

| Token | Format | Lifetime | Travels in |
|---|---|---|---|
| Access token | JWT signed with HS256 | 15 minutes | `Authorization: Bearer` header |
| Refresh token | Opaque, random | 7 days | `HttpOnly`, `Secure`, `SameSite=Strict` cookie scoped to `/api/auth` |

- **The signature is mandatory.** Key of at least 256 bits read from a secret. Reject any token that is
  unsigned, uses `alg: none` or uses an algorithm other than the configured one.
- Access token claims: `sub` (user id), `role`, `jti`, `iat`, `exp`. No personal data.
- The refresh token is stored in **Redis as a hash only**, with a TTL equal to its lifetime. The cookie
  is the only one the API issues.
- **Rotation**: every `/api/auth/refresh` call invalidates the token used and issues a new one. Reusing
  a consumed token revokes the whole session.
- **Logout**: the access token's `jti` goes to the **Redis denylist** with a TTL equal to its remaining
  life, and the refresh token is deleted. The filter checks the denylist on every request.
- Changing the password, locking or deactivating an account revokes all its refresh tokens.

## Password recovery

- Random 6-digit code by email, valid for 15 minutes, single-use.
- Only the hash is stored (`password_reset_codes.code_hash`); 5 failed attempts invalidate the code.
- The response is identical whether or not the email exists.

## Rate limiting

Counters in Redis. Over the limit: **429** with `Retry-After` in seconds and a `ProblemDetail` body.

| Endpoint | Limit | Key |
|---|---|---|
| Login | 5 attempts / 15 min | email |
| Login | 20 attempts / 15 min | IP |
| Registration | 5 / hour | IP |
| Request a verification or recovery code | 3 / hour, 60 s between sends | email |
| Request a verification or recovery code | 10 / hour | IP |
| Check a verification or recovery code | 5 attempts per code | code |
| Token refresh | 10 / min | user |
| Authenticated API in general | 120 / min | user |
| Catalog search | 30 / min | user |
| PDF/XLSX exports | 10 / hour | user |
| Assistant chat | 10 / min and 100 / day | user |
| RAG ingestion and re-indexing | 5 / hour | user (`ADMIN`) |

- Email-keyed limits apply whether or not the account exists.
- Every new public endpoint declares its own limit; authenticated ones inherit the general limit.
- Each limit has a test that checks the 429 when it is exceeded.

## Secrets

Environment variables or Docker Secrets (Secrets Manager on AWS). Never in the repository, in versioned
`application*.yml`, in tests or in logs.
